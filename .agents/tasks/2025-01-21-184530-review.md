# Loyalty points system data fix

The loyalty points system showed 0 points for all customers because the seed data contained no completed, fully-paid events. The fix adds three completed events with full payment chains: Event 1 (existing wedding, now marked completed and paid), Event 6 (anniversary for customer 1), and Event 7 (product launch for customer 2).

**Watch for:** Event IDs 6 and 7 in payments INSERT assume auto-increment, but invoices INSERT hardcodes them, creating a schema dependency risk (possible).

**Verdict**: APPROVED

## High-level view

Three events now meet all eligibility criteria: Event 1 gets an additional 470K payment to reach 720K total, matching the invoice; Event 6 adds a 125K fully-paid anniversary for customer 1; Event 7 adds a 180K fully-paid product launch for customer 2. All three have status='Completed', invoices with matching customer_id, and payments summing to invoice totals with correct customer_id and event_id foreign keys. Customer 1 ends with 200 points (2 events), customer 2 with 100 points (1 event), customer 3 with 0 points.

The LoyaltyService SQL eligibility check references payments.customer_id and payments.event_id, both present in the schema. No column name mismatches detected between Java and database.

## Schema alignment with LoyaltyService SQL

The LoyaltyService eligibility check references `payments.customer_id` and `payments.event_id`:
```sql
COALESCE((SELECT SUM(p.amount) FROM payments p 
          WHERE p.invoice_id = i.invoice_id
          AND p.customer_id = e.customer_id 
          AND p.event_id = e.event_id), 0) < i.total_amount
```

Both columns exist in the schema (lines 241-260). The investigation report flagged this as a potential issue, but the columns are present.

## Event ID hardcoding in invoices and payments

The loyalty fix SQL adds invoices with hardcoded event_id values:
```sql
INSERT INTO invoices
    (event_id, customer_id, invoice_number, ...)
VALUES
(6, 1, 'INV-2025-020', ...),
(7, 2, 'INV-2025-030', ...);
```

Then payments reference invoice_id=4 and 5:
```sql
INSERT INTO payments
    (invoice_id, event_id, customer_id, ...)
VALUES
(4, 6, 1, 125000.00, ...),
(5, 7, 2, 180000.00, ...);
```

This assumes:
- Events 1-5 are the only events in the table before this script runs, so the new events get IDs 6 and 7.
- Invoices 1-3 are the only invoices before this script, so the new invoices get IDs 4 and 5.

If the database already contains additional rows (from manual testing, partial runs, or other seed data), the IDs will mismatch and the foreign key constraints will either fail or point to the wrong records. The comment in the fix acknowledges this ("they'll be 6 and 7") but doesn't guard against it.

A safer approach: fetch SCOPE_IDENTITY() after the events INSERT and use variables, or rely on invoice_number lookups rather than hardcoded IDs. For a single-use seed script on a fresh database, this is acceptable but fragile.
